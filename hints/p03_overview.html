P03 · Orchestrator v2：async_chunk 预热 + 终态守门

题面速览

  • 在系统中的位置：thinker 每 decode 一个 token 就把向量经 connector 发给 talker，talker 每攒够一个窗口就把 codec 发给 code2wav——数据不经过 orchestrator。orchestrator 只剩两件事：请求到达时预热下游 stage（提交占位请求，让它在 scheduler 里等第一个 chunk），以及守门终态。
  • 为什么预热：等 thinker 产出第一个 chunk 才提交 talker，就多一次 “stage→orchestrator→stage” 往返；预热后第一个 chunk 一落地 talker 就能开始。
  • 为什么守门：
时间 →
stage2 (audio, final):  ... wav5(fin)           ← 控制面上先到
stage1 (talker):        ............... (fin)   ← 晚到（它的 IPC 慢了一拍）
如果在 wav5(fin) 时就发 finished 并清理：
 - 清理会回收 stage1 仍在使用的资源（SHM、绑定）
 - stage1 的完成消息成了“未知请求”的输出
  • 规则：最后一个 final stage 完成、但 submitted ⊄ finished 时，把终态消息存进 pending_final；等最后一个已提交 stage 也完成时再发出。仍然要求恰好一条终态且为最后一条。
  • 需求清单：add：注册状态 → 把 0..last 都标记为 submitted → 先提交 stage 0（真实 prompt），再提交下游（prewarm_fn(sid, prompt) 占位）· 不做任何转发 · 清理后到达的输出丢弃计数，状态不复活。本题直接继承你的 P02，覆盖 _handle_add 和 _handle_output。

验收要点：每个 stage 只被提交一次、下游拿到 prewarm 占位输入 · 非 final 的 stage1 迟 200ms 才报告完成时终态必须等它 · 20 个请求 + 迟到完成：每个请求恰好一个终态且是最后一条 · 清理后到达的输出被丢弃、状态不复活。

直觉与类比

车间主任和传送带

P02：每道工序做完一整批零件交给车间主任，主任搬到下一道工序。P03：工序之间装了传送带（connector），上一道每做好一个零件就直接放上去——流水线并行起来。车间主任不再搬零件，只剩两件事：① 开工时通知所有工序“有新订单，准备接传送带”（prewarm）；② 收工时确认每一道工序都停机了，才给客户签收单（终态守门）。

快递和签收短信

货物走物流（数据面），“已发货/已完成”走短信（控制面）。最后一站的签收短信可能比中转站的“已出库”短信先到。你一看到“已签收”就把订单归档删除，几秒后中转站的短信到了你却找不到这张订单；更糟的是归档时你可能已经把中转站还在用的托盘（共享内存、绑定）收回了。

框架视角 · 只有两处变了

和 P02 相比
T 不变：同一个事件循环里的 task。新增的 connector 是 stage 进程之间的边界，orchestrator 不碰它
S ReqState 多用一个字段 pending_final；submitted 的含义变成“预热过的所有 stage”；stage_data 不再需要
B / W / C 完全不变：reader × N、request_handler、dispatcher、三个队列——所以 P03 能直接继承 P02
L / I 不变
F 变了：add 时一次性标记 submitted；终态条件多了 submitted ⊆ finished；非 final stage 的完成事件也可能触发发送（放行 pending_final）
E 清理后再到的输出照样丢弃计数，绝不能因为 S1 的迟到完成消息而重新建出状态

易错点

  • 沿用 P02 只标 {0}：S2 最后一块到达时 {0} ⊆ {0,2} 成立，终态提前发出并清理；S1 迟到的完成报告变成 dropped。
  • 非 final stage 完成时不检查 pending_final：用户永远收不到终态，next_output 超时，request_states 泄漏。
  • 存进 pending_final 的同时也发了出去，或发 pending 后忘记清理：终态重复或状态泄漏。
  • 直接沿用 P02 的 _handle_output：S0 完成时会调用 forward_fn 并 submit S1——S1 被 submit 两次，第二次输入是 None。
  • 未知 id 时复活状态（setdefault）：新 ReqState 的 submitted 为空，门形同虚设，迟到输出被发给用户、出现在终态之后，状态永久泄漏。

▶ final={0,2}，prewarm_fn = lambda sid, p: f"warm{sid}:{len(p)}"，add_request("r1", "hi there")
1. add：一次性标记、依次 submit

注册 → submitted = {0,1,2}（在第一次 await 之前）→ S0.submit("r1", "hi there") → S1.submit("r1", "warm1:8") → S2.submit("r1", "warm2:8")。每个 stage 只 submit 一次。

2. S0 ("hi", False)

finished = {}；all_final = F；all_done = F → 发 (0,'hi',F)。

3. S0 ("there", True)

finished = {0}；all_final = F → 发 (0,'there',F)。不转发。

4. S2 ("wav:HI", False)

finished = {0} → 发 (2,'wav:HI',F)。

5. S2 ("wav:THERE", True)：扣下终态

finished = {0,2}；all_final = T；all_done = {0,1,2} ⊆ {0,2} = F

→ 构造 (2,'wav:THERE',T) 存进 pending_final，什么都不发，return。

6. S1 (None, True)：最后一块拼图

finished = {0,1,2}；S1 不是 final，但 all_done 成立且 pending 不为空 → 发出 (2,'wav:THERE',T)，清理。

7. S2 ("wav:EXTRA", False)

状态已清理 → dropped_outputs == 1，不复活。

细节

  • 构造函数里 forward_fn=lambda *_: None 只是为了满足父类签名。
  • 提交顺序：先 S0（真实 prompt），再 S1、S2……（占位），范围 0..last_stage。
  • 两道门：OrchOutput.finished 的取值仍是 P02 的“所有 final stage 都完成”；但 finished=True 的消息何时发出多了一个条件 submitted ⊆ finished。
  • pending_final 存的是已构造好的 finished=True 的 OrchOutput，之后原样发出。
  • 如果你的 P02 把这两步写死在 dispatcher 里而不是独立方法，先回去重构 P02。
L2思路与常见坑思路拆分与常见坑（中度剧透）
  • add 路径：建 ReqState → 注册 → submitted = {0..last}（全部同步）→ await S0.submit(prompt) → 依次 await S_k.submit(prewarm_fn(k, prompt))。
  • 输出路径决策表（先查状态、未知就 drop；若 finished 就加入 st.finished）：
这条输出来自 all_final（final ⊆ finished） all_done（submitted ⊆ finished） 动作
final stage 否 — 发 OrchOutput(..., finished=False)
final stage 是 是 发 finished=True 的消息，清理
final stage 是 否 构造 finished=True 的消息，存进 pending_final，不发
非 final stage — 是，且有 pending_final 发 pending_final，清理
非 final stage — 其他 什么都不做
  • submitted 是守门的依据：少一个 stage，门就少一道。在第一次 await 之前一次性标完，和 P02“先注册再 submit”是同一个原则。

关键问题答案
  1. 只标 {0} 时，S2 的 "wav:THERE" 到达那一刻 finished={0,2}，{0} ⊆ {0,2} 成立，终态立即发出并清理——正是本题要防止的“提前终态”；随后 S1 的完成报告变成未知 id，dropped_outputs == 1。在第一次 await 前标完，则无论哪个 await 点插进来的输出，看到的都是完整的 submitted。
  2. 什么都不发。构造 finished=True 的 OrchOutput，存进 st.pending_final，直接 return。
  3. 把 sid 加进 finished 后检查 submitted ⊆ finished 且 pending_final is not None：都成立就发出 pending 并清理。pending 为空（还有 final stage 没完成，例 2 的 S1）时什么都不做。
  4. all_final = final_stage_ids ⊆ finished：决定 OrchOutput.finished 的值。all_done = submitted ⊆ finished：决定 finished=True 的消息立即发出（并清理）还是先扣在 pending_final。
  5. 不会；非 final stage 的输出只用来更新 finished。stage_data 不需要。
  6. start / shutdown / add_request / next_output / reader / dispatcher / request handler / _cleanup 全部复用；只换 _handle_add 和 _handle_output。
  7. 它不是 finished，不改变任何集合，落入“什么都不做”。
