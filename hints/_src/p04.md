lede: 每个 stage 可以有多个 replica：请求一旦落在某个 replica 上就必须一直在那（KV 在那）；客户端断开要 abort；某个 replica 进程死了，只能让绑定在它上面的请求失败。

## 题面速览

- **在系统中的位置**：deploy 里 `num_replicas: 2` 会给一个 stage 起两个独立的 EngineCore 进程；orchestrator 为每个逻辑 stage 维护一个 `StagePool` 负责选 replica。
- **粘性绑定**：请求的 KV cache、流式输入中间状态都在第一次分配到的 replica 上；后续 update / abort / 下一个 chunk 必须找同一个 replica。新请求在存活 replica 之间 round-robin。
- **两阶段 abort**：

```
① partial = processor.collect_partial(rid)    # 只读：拿到已生成的部分文本，用于最后一条输出
② for pool: await pool.abort([rid])           # 引擎侧真正停止；失败就抛出，不进入 ③
③ processor.commit_abort(rid)                 # 提交：丢弃 detokenizer 状态
return OrchOutput(rid, partial, finished=True, error="abort")
```

  ③ 先于 ②：引擎 abort 失败时 processor 已忘了这个请求，引擎却还在产出 token——孤儿输出。同一 replica 上的多个请求要**合并成一次 abort 调用**（一次 IPC）。
- **故障隔离**：replica 崩溃（reader 收到 EngineDead）→ 标记死亡，只让绑定在它上面的请求以错误结束；其他照常；新请求不再分给它。全死了 `pick` 抛 `NoLiveReplica`。

**验收要点**：round-robin + 粘性 · evict 返回受影响请求、之后不再分配到死 replica、无存活时抛 NoLiveReplica · abort 按 replica 分组、每个 replica 只调用一次 · 两阶段顺序 collect → 各 stage abort → commit · abort 失败时不 commit、保留绑定以便重试 · 死 replica 只让绑定在它上面的请求失败。

## 直觉与类比

::: callout analogy 行李寄存柜台（粘性绑定）
火车站有 3 个寄存柜台（replica）。第一次来按顺序分到某个柜台（round-robin），行李（KV cache）就存在那。之后续存、取、退，必须回同一个柜台。某个柜台关门了（evict），就只在开着的柜台之间轮；关门时要通知在那儿存过东西的旅客（handle_dead_replica），并把登记本上这几行划掉——否则下次有人拿着旧登记去找，只会找到一扇关着的门。

① 拍照（collect_partial，只读）：先把做好的半成品拍下来；② 通知每家工厂停工（await abort）：电话打不通就停下，**别销账**；③ 销账（commit_abort，不可逆）：所有工厂确认停工后才把订单从账本删掉；最后发“已取消”通知附上照片。先销账再打电话、电话又没打通：工厂继续做，货送回来账本上查无此单（孤儿输出），想重试照片也找不回来了。

## 易错点

- 每个 id 调用一次 replica.abort：结果对，但 IPC 次数 = 请求数。
- await 之前就释放绑定：abort 失败后 bound() 变 None，重试时找不到 replica，请求在引擎里继续跑成孤儿。
- evict 只标记不删绑定：pick 可能对旧请求返回死 replica；之后 abort 这些请求会去调用死进程。
- 用 `asyncio.gather` 并发所有组：一组失败时其他组可能成功也可能没执行完，绑定释放时机难以推理。
- commit 放在 abort 之前，或用 try/finally 保证 commit：abort 失败时前端已忘记请求，引擎却还在吐 token。
- “对全部 replica 取模再跳过死的”：死 replica 的下一个邻居多拿一份。
- 遍历 dict 时删除（先收集再删）。

## 三级提示

::: hint 1 I/O 示例与关键问题
例 1、例 2 见上方逐步图。

**例 3：两阶段 abort 与死 replica**。三个 stage 池 s0/s1/s2，"r9" 分别绑在 T0、K1、W0；processor 里 r9 的部分文本 "Hello wor"：

```
out = await abort_request([s0, s1, s2], proc, "r9")
调用顺序：collect_partial("r9") -> T0.abort(["r9"]) -> K1.abort(["r9"]) -> W0.abort(["r9"]) -> commit_abort("r9")
out == OrchOutput("r9", "Hello wor", finished=True, error="abort")

换一组池：s0 = [T0]，s1' = [K0]，K0.abort 会抛 RuntimeError
await abort_request([s0, s1'], proc, "r9")   # -> 抛出 RuntimeError
调用顺序：collect_partial -> T0.abort(["r9"]) -> K0.abort(["r9"]) 抛错    # 没有 commit_abort
s0.bound("r9") is None（成功，已释放）；s1'.bound("r9") == 0（保留，可重试）
```

死 replica：`d = StagePool(2, [W0, W1])`，a,b,c 依次 pick 到 0,1,0。`handle_dead_replica(d, 0)` → a、c 各一条 `OrchOutput(..., None, finished=True, error="stage 2 replica 0 died")`；`d.bound("b") == 1`；`d.live_replicas() == [1]`；再 `d.evict(1)` 后 `d.pick("new")` 抛 NoLiveReplica。error 文字由你决定，非空、能说明原因即可。

#### 关键问题

1. 绑定表是什么形状？pick 对已绑定和未绑定的请求分别做什么？粘性命中时计数器要前进吗？
2. round-robin 只在存活 replica 间轮转：“对存活列表取模”还是“对全部取模再跳过死的”？evict 后表现有什么不同？
3. evict 为什么要删掉绑定而不是只标记死亡？
4. abort(ids) 里 5 个 id 分布在 2 个 replica 上，应该产生几次调用？无绑定的 id 呢？没有 id 的 replica 要不要调用？
5. 例 2 中 A 成功、B 抛错：哪些绑定释放、哪些保留？为什么“先释放再 await”是错的？
6. 为什么 collect_partial 必须在引擎 abort 之前、commit_abort 必须在之后？
7. abort_request 对一个根本没绑定 r9 的池调用 `pool.abort(['r9'])` 会怎样？需要在外面先判断吗？

#### 细节

- replica id = 下标；`live_replicas()` 按下标升序返回。
- bound 只读（没有就 None，不创建）；pick 可能创建；release 是正常结束时删除，对不存在的 id 不报错。
- 本题的 `OrchOutput(request_id, data, finished, error)` 没有 stage_id 字段；abort 的终态 error 固定是 `"abort"`；死 replica 的终态 data 为 None。
- 两阶段和数据库的 prepare/commit 是同一种思路：不可逆的那一步放在最后。
:::

::: hint 2 思路与常见坑
- **状态**：`alive: list[bool]`、`bindings: dict[str, int]`、round-robin 计数器；全部同步方法，唯一的 await 在 abort 里。
- **pick**：已绑定且活着 → 返回；否则取存活列表，空则 NoLiveReplica；`live[rr % len(live)]`，rr += 1，写绑定。
- **evict**：标记死亡 → 找出所有绑在它上面的 request → 删除 → 返回列表。
- **StagePool.abort**：① 用绑定表分组成 `{replica: [ids]}`，无绑定跳过；② 对每组 `await replicas[rep].abort(ids)`，**这一组成功返回之后**再释放这组的绑定；③ 任一组抛错就传出去——已成功的组已释放，失败组和尚未处理的组保留。
- **abort_request**：collect → 对每个 pool 顺序 `await pool.abort([rid])`（不要 try/except 吞错）→ commit → 返回终态。
- **handle_dead_replica**：`pool.evict(replica)` + 每个受影响请求一条终态错误输出。
:::

::: hint 3 详解：答案
::: answer 关键问题答案
1. `dict[request_id, replica_id]`。已绑定且活着 → 返回；否则轮转选择并写入。粘性命中不推进计数器（推进也不算错，但分配不均）。
2. 建议对存活列表取模：evict 后自动只在活着的里面均匀轮转；另一种写法要处理“跳过”且分布会偏。
3. 绑定代表“这个请求在那个 replica 上有状态”；replica 死了状态就没了，保留绑定会让 pick 返回死 replica、abort 调用死进程。删掉后这些请求已由 handle_dead_replica 发了错误终态。
4. 2 次（每个有 id 的 replica 一次）；无绑定的 id 忽略；没有 id 的 replica 不调用。
5. A 那组（m、o）释放，B 那组（n）保留，异常抛出。先释放再 await：失败时绑定已经没了，重试无从下手。
6. collect 在前：commit 会丢掉前端状态，之后拿不到部分文本；commit 在后：只有引擎都确认停止，前端才能安全地忘记这个请求。commit 在前 + abort 失败 = 引擎还在产出、前端不认识它（孤儿输出），而且用户已经收到 abort 终态。
7. 该池分组为空，不会产生任何 replica 调用，直接返回。不需要外面判断。
:::
:::
